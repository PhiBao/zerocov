# ZeroCov — IBM Bob 2.0 Hackathon Submission

## Project Name
**ZeroCov: From Test Debt to Production-Ready in One IBM Bob 2.0 Session**

## One-Sentence Description
ZeroCov is a structured IBM Bob 2.0 workflow that takes a real-shaped Node.js/TypeScript API from 22.8% test coverage to 89.5% in a single session — using document understanding, Plan mode, four parallel subagents, and an agentic run-read-fix verification loop that catches spec divergences along the way.

---

## Problem Statement

Every engineering team has the same conversation: *"We'll write tests next sprint."* They don't. Six months later, critical paths — authentication, expense handling, approval workflows — have zero test coverage. A developer gets assigned to "fix coverage." The estimate: 2–3 weeks.

This is not a discipline problem. It is a tooling problem.

Writing comprehensive tests for an existing codebase requires:
1. Understanding the *intended* behavior (from specs, not just code)
2. Covering multiple test layers simultaneously (unit, integration, E2E)
3. Running tests, reading failures, and fixing both bad tests and real defects
4. Doing all of this systematically, not ad hoc

**IBM Bob 2.0 does all four.**

---

## Solution: ZeroCov

ZeroCov is a six-step IBM Bob 2.0 workflow applied to a realistic expense-tracking REST API (the **ExpenseFlow API**) that is deliberately published with a thin 22.8% baseline — mirroring what most production codebases look like after six months of feature work.

```
STEP 1 — ASSESS      Bob reads openapi.yaml, auth-security-requirements.md,
                     approval-workflow.md, and AGENTS.md (document understanding)
STEP 2 — STRATEGIZE  Plan mode creates TEST-STRATEGY.md for human review & approval
STEP 3 — EXECUTE     4 parallel subagents write tests for all layers simultaneously
STEP 4 — VERIFY      Agent mode runs tests, reads failures, fixes source defects
STEP 5 — REPORT      Coverage diff: 22.8% → 89.5%, findings documented
STEP 6 — READY       Session output prepared as a reviewable PR
```

**Final result**: 145 tests, 89.5% statement coverage, 2 spec divergences detected and fixed, in approximately 25 minutes.

### Honest framing of the fixture

ExpenseFlow is a synthetic fixture, and the two divergences (below) were introduced deliberately so the workflow can be demonstrated end-to-end from a controlled baseline. The claim here is **not** "Bob found surprise bugs in an unknown codebase." The claim is that spec-driven tests generated by Bob reliably catch implementation/spec divergence — and that is demonstrated reproducibly, with the failing tests preserved in git history.

## IBM Bob 2.0 Usage Statement

IBM Bob 2.0 is the **core engine** of the entire workflow. Every significant action is performed by Bob. The sample project exists solely to give the workflow something real to operate on.

### Feature 1: Agent Mode

**Where used**: Step 3 (writing test files across 9 suites), Step 4 (running `pnpm test:coverage`, reading terminal output, diagnosing failures, fixing `src/auth/middleware.ts` and `src/expenses/routes.ts`), Step 5 (generating the coverage report), Step 6 (PR preparation).

**Why it is load-bearing**: Agent mode is the only mode that can write files, execute terminal commands, read the output, and iterate. Without it, tests can be written but never verified. The verification loop (run → read failure → fix source → re-run) is what turns test writing into an autonomous engineering session.

**Specific demonstration**: Agent mode reads the failing assertion, cross-references `docs/auth-security-requirements.md`, identifies the divergence in the middleware catch block, applies the fix, re-runs the suite, and confirms 145/145 passing.

### Feature 2: Parallel Tasks / Subagents

**Where used**: Step 3 — four subagents run simultaneously, each with an isolated context window focused on one test layer.

| Subagent | Scope | Output |
|---|---|---|
| `auth-tests` | JWT tokens, middleware, auth routes | `tests/unit/auth/*` |
| `api-tests` | Expenses, approvals, reports handlers | `tests/unit/expenses/`, `tests/unit/approvals/`, `tests/unit/reports/` |
| `integration-tests` | Full approval workflow end-to-end | `tests/integration/` |
| `utils-tests` | Utility functions + error classes | `tests/unit/utils/helpers.extended.test.ts` |

**Why it is load-bearing**: Sequential test writing — even with AI — takes proportional time. The 4× parallelism converts hours into minutes. Isolated context also produces better tests: each subagent only holds its layer's source and spec sections.

### Feature 3: Document Understanding

**Where used**: Step 1 and throughout — Bob attaches `openapi.yaml`, `docs/auth-security-requirements.md`, and `docs/approval-workflow.md` before any test writing begins.

**Why it is load-bearing**: This is what makes the tests spec-driven rather than implementation-driven. Without the documents:
- A code-only test of expired tokens would have asserted 500 and locked in the divergence
- Integration tests would be guessed rather than derived from the state machine
- The amount-validation divergence (non-integer / non-finite / above-cap values accepted despite `type: integer, minimum: 1`) would never be asserted

**Specific demonstration**: the `auth-tests` subagent reads `EXP-TOKEN-401` and asserts 401. The test fails (gets 500). That failure is the detection mechanism for a divergence that is invisible to code-only analysis, because the code is *consistent* — consistently wrong.

### Feature 4: Plan Mode

**Where used**: Step 2 — Bob produces `TEST-STRATEGY.md` before writing any tests.

**Why it is load-bearing**: Plan mode forces a whole-workflow strategy — risk-ranking modules, assigning test layers, deriving test scenarios from the specs — before implementation. The human approval gate ensures the strategy is right before four agents work in parallel.

**Additional Bob features used**:
- **SKILL.md (`test-strategist`)**: structured output format for `TEST-STRATEGY.md` plus supertest/`db.reset()`/`generateAuthTokens()` patterns
- **Custom rules (`.bob/rules/testing-standards.md`)**: spec-driven testing standards enforced across all subagents
- **`AGENTS.md`**: persistent project context (architecture, conventions, spec-first rule)

## Why This Demonstrates IBM Bob 2.0's Value

Other AI coding tools can suggest tests. The combination Bob 2.0 provides is different:

1. **Reads the specification and writes tests that catch implementation/spec divergence** — document understanding makes the expected value come from the contract, not the code.
2. **Writes four test layers simultaneously** — parallel subagents create a genuine speed advantage over sequential generation.
3. **Runs tests, reads failures, and fixes source defects in a loop** — Agent mode closes the gap between "tests written" and "tests working."
4. **Governed by Plan mode and custom rules** — human review before implementation, and a rule that forbids weakening assertions to make tests pass.

## Reproducing the Demo

```bash
pnpm install
git checkout zerocov-baseline && pnpm test:coverage   # 22.77% statements, 14 tests
git checkout main && pnpm test:coverage               # 89.46% statements, 145 tests
```

Then open a fresh worktree of `zerocov-baseline` in IBM Bob 2.0 and follow `BOB-SESSION-PLAYBOOK.md`.
